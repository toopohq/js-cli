# Decisions

One line per decision, newest last.

- 2026-09-24 — The toolchain and its checks are those of `spec` and `js`, at the same versions: Biome capping a file at 150 lines and a function at 40, a warning failing like an error; TypeScript 7; Vitest; knip; CI on Node 24. One project, one policy.
- 2026-09-24 — The client has no runtime dependencies. Node covers what it needs (`fetch`, `node:crypto`, `util.parseArgs`, `node:readline/promises`), and `npx toopo` downloads the client alone. The hook refuses a `dependencies`, `optionalDependencies` or `peerDependencies` field on a write, CI on every pull request, since `pnpm add` in a shell bypasses the hook: npm installs all three with the client. `spec` and `js` refuse `dependencies` alone, since no user installs either.
- 2026-09-24 — The client runs on Node 22.13 and later, on the oldest line still maintained, until April 2027; the toolchain runs on 24. `@types/node` is pinned to 22, so `tsc` refuses a Node API Node 22 does not have; `tsconfig.json` names it, since TypeScript 7 includes no `@types` package unless named. `lib` is ES2024, so it refuses a built-in Node 22 lacks, as `lib` holds the catalogue to its baseline: `esnext` passed `RegExp.escape` and `Promise.try`, and its DOM a `document`. `target` is ES2024, so the emit lowers a syntax Node 22 does not parse, `using` for one. What Node 22 has of ES2025 joins `lib` when the client needs it. `engines` says `>=22.13`, the first release on which the `require` line `add` prints for a `.mjs` loads with no warning; Node maintains a line through its newest release alone. Known ceilings: an API added to 22 before 22.20, the types' version, passes `tsc` and fails on an older 22; 23.0 to 23.4, a line Node no longer maintains, pass `engines` and warn; CI tests the behaviour on Node 24 alone, and 0.1.0 was run by hand on Node 22.23.3, packed, against `toopo.dev`.
- 2026-09-24 — The published client is JavaScript: Node strips no types under `node_modules`. `tsconfig.build.json` has `tsc` emit `dist/` from `src/main.ts` and what it imports, so no test ships, and `rewriteRelativeImportExtensions` turns `./add.ts` into `./add.js`; `prepack` runs it, and `files` publishes `dist/` alone. Nothing is bundled: `spec` enters by `import type` alone, which the emit erases, and npm installs no devDependency, so a value import would fail at the user's. CI packs the client on every pull request, unpacks it outside the repository, where no devDependency resolves, and runs its `bin`, `init --ts`: a static import the user's install lacks fails there, as does a `.ts` specifier left in `dist/`, a `bin` naming no emitted file or a `files` leaving one out; a grep of `dist/` for bare specifiers passed `import 'typescript'`. knip names `src/main.ts` as an entry, since `bin` points at `dist/main.js`. Known ceilings: a dynamic import fails only on the path that runs it; `prepack` does not empty `dist/`, so a release is published from a fresh clone.
- 2026-09-24 — `@toopo/spec` joins the devDependencies with its first import: knip refuses a dependency nothing imports.
- 2026-09-24 — No Stryker: mutation testing is the catalogue's, scoped to the files a user copies. The client is tested by Vitest.
- 2026-09-24 — CI refuses `Co-Authored-By`, `Claude` and `Generated with` anywhere in a pull request's title, body or commits, a human co-author and a mention of the tool included: a false alarm costs a reworded message, a missed attribution is published for good.
- 2026-09-24 — `toopo.json` holds `emission`, `"ts"` or `"js"`, the key of the served record's `emissions`, `extension`, the file's, and `folder`, where `add` writes. A field joins with the command that reads it. `init` writes `folder` unasked: `src/toopo` when `src/` exists, `toopo` otherwise; the file is the user's to edit.
- 2026-09-24 — `init` detects TypeScript by a `tsconfig.json` in the working directory and asks, the detection as the default; `--ts` or `--js` skips the question. Known ceiling: it neither walks up to a project root nor looks for TypeScript in `package.json`, and the answer corrects what the file misses. A stdin that closes unanswered fails and names the flags. The answer is readline's first line, not `question()`'s, which never settles when stdin ends, so Node exits 13, and drops a last line with no newline: `printf ts | toopo init` lost its answer.
- 2026-09-24 — `init` refuses an existing `toopo.json`, before asking: rewriting a user's configuration is the user's to do.
- 2026-09-24 — `toopo add <domain>/<name>` fetches `js/<domain>/<name>.json`, the tree's own file rather than the rewrite a browser uses, which Pages caps at 2,000 rules. The record is typed by `spec`'s `ServedRecord` through `import type`, which Node strips, so `spec` stays a devDependency. The record's `address` must equal the one asked: the registry serves only addresses `spec` accepts, so the check also keeps `..` out of the local path. A non-empty `dependencies` fails, as `spec` requires, and so does a missing emission. The file's sha256 is verified before anything is written. It lands at `<folder>/<domain>/<name>.<extension>`, refused when it exists and written `wx`: once copied, it is the user's. `toopo.lock` is `{ [address]: { version, sha256 } }`, merged into an existing one, which is read before anything is written: a lock that fails to parse after the copy would leave a file no second `add` can lock. The registry is `https://toopo.dev`; `TOOPO_REGISTRY` overrides it, so the tests serve a fake one on a local HTTP server. Known ceiling, as for `init`: `toopo.json` and `toopo.lock` are read in the working directory alone.
- 2026-09-24 — The first release is 0.1.0: npm never reuses a version, and the old project's `toopo`, unpublished, took 1.0.0 to 1.2.0. It is published by hand from a fresh clone of `main`, since npm configures a trusted publisher only for a package that exists.
- 2026-09-24 — The catalogue delivers ESM, and Node reads a `.js` file as the nearest `package.json`'s `type` says: under `"type": "commonjs"`, `require` and `import` of the delivered `.js` both fail on Node 24; with no `type`, it loads after a second parse, and a warning. `init` reads `type` in the working directory, before asking, past a BOM, which Node and npm accept and `JSON.parse` refuses, and the `.js` emission of a project whose `type` is not `module`, a missing field or file included, lands as `.mjs`, which Node loads as ESM whatever `type` says, from `require` since 22.12. `toopo.json` records it as `extension`, which `add` reads. The `.ts` emission keeps `.ts`: `tsc` compiles its `export` to the project's module format. Known ceiling: under CommonJS, `verbatimModuleSyntax` and Node's own type stripping refuse that `export`; `.mts` answers both, when a user needs it.
- 2026-09-24 — `add` prints on stdout the file it wrote, then the line that imports it: a user importing the path on disk got TS5097, `tsc` refusing a `.ts` specifier without `allowImportingTsExtensions`. The specifier names `.js` for `.ts` and `.mjs` for `.mts`, uses `/` on Windows too, and is relative to the folder's parent, `src/` for `src/toopo`, where an entry usually sits. The name imported is the address's last segment in camelCase, `deep-equal` as `deepEqual`: the record names no export. A `.mjs` prints `const { x } = require(…)` instead: `init` writes `.mjs` for a CommonJS project, whose `.js` files throw a SyntaxError on `import`; run by hand, `type` `commonjs` or absent, the line loads the function with no warning on Node 22.13.0, 22.23.3, 23.5.0 and 24.21.0, with an `ExperimentalWarning` on 22.12.0 and 23.4.0, and throws `ERR_REQUIRE_ESM` on 22.11.0. Known ceilings: a file elsewhere adjusts the `./`; a project with no `type` whose `.js` Node detects as ESM, where `require` is undefined, `import`s the `.mjs`; a project that runs its `.ts` by Node's type stripping, under `allowImportingTsExtensions`, names `.ts`; an export named otherwise makes the line wrong, until the record names its exports.
